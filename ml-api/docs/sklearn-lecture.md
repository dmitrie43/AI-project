## 1. `train_test_split`

**Модуль:** `sklearn.model_selection`

**Зачем:** разрезать X и y на train и val (у нас 80/20).

```python
x_train, x_val, y_train, y_val = train_test_split(
    x, y,
    test_size=0.2,
    random_state=42,
    stratify=y,
)
```

### Аргументы


| Аргумент        | Влияние                                      |
| --------------- | -------------------------------------------- |
| `test_size=0.2` | 20% → val, 80% → train                       |
| `random_state`  | фиксирует перемешивание → одинаковый результат |
| `stratify=y`    | доля классов в train/val почти как во всём y |


### Выход

Четыре объекта: `x_train`, `x_val`, `y_train`, `y_val`.

**Дальше:** для честного экзамена иногда делают два сплита (train+val, потом test) или режут по `created_at`.

## 2. `Pipeline`

**Модуль:** `sklearn.pipeline`

**Зачем:** склеить шаги в один объект: препроцессинг → модель.

```python
Pipeline(steps=[("preprocess", preprocess), ("clf", clf)])
```

### Аргументы


| Аргумент | Смысл |
| -------- | ----- |
| `steps`  | список `(имя, объект)` по порядку |


### Методы (главные)


| Метод | Что делает | Выход |
| ----- | ---------- | ----- |
| `fit(X, y)` | учит все шаги по очереди | сам pipeline (обученный) |
| `predict(X)` | препроцессинг + класс | массив меток `0/1` |
| `predict_proba(X)` | препроцессинг + вероятности | массив shape `(n, 2)` |


**Зачем нужен:** при сохранении в `model.joblib` и в `/predict` один и тот же путь обработки.

## 3. `ColumnTransformer`

**Модуль:** `sklearn.compose`

**Зачем:** разные колонки — разная обработка (категории vs числа).

```python
ColumnTransformer(transformers=[
    ("cat", OneHotEncoder(...), ["category"]),
    ("num", Pipeline([...]), ["priority", "satisfaction", "tag_count"]),
])
```

### Аргументы


| Аргумент | Влияние |
| -------- | ------- |
| `transformers` | список `(имя, transformer, список_колонок)` |
| `remainder` (по умолчанию `drop`) | колонки не из списка — отбросить |


### Выход после `fit_transform` / внутри Pipeline

Числовая матрица признаков (one-hot + imputed numbers).

## 6. `LogisticRegression` — подробно (лекция)

**Модуль:** `sklearn.linear_model`  
**Задача у нас:** по признакам тикета сказать `is_open` = 0 (resolved) или 1 (open/in_progress).

Ниже — как если объяснять студенту, который видит тему впервые.

### 6.1. Какую задачу решает

Есть таблица истории:

- слева признаки X (category, priority, …);
- справа правильный ответ y (0 или 1).

Нужно правило, которое для **нового** тикета выдаст 0 или 1.

Можно было бы придумать if-ы вручную. LogisticRegression **подбирает числа-веса** по данным так, чтобы чаще угадывать y.

Это **бинарная классификация** (два класса). Не регрессия «предсказать число часов» — слово regression в названии историческое.

### 6.2. Что модель получает на вход

К моменту LogisticRegression Pipeline уже сделал:

1. `category="vpn"` → one-hot, например `[1, 0, 0, 0, 0]`;
2. числа + imputer → например `priority=4`, `satisfaction=3`, `tag_count=2`.

На вход классификатора попадает **один длинный вектор чисел** \(x = (x_1, x_2, \ldots, x_n)\).  
Строк и `NaN` там уже нет.

### 6.3. Шаг 1 — линейный балл z

Модель хранит веса \(w_1, w_2, \ldots, w_n\) и сдвиг \(b\).

Считается одно число:

\[
z = w_1 x_1 + w_2 x_2 + \ldots + w_n x_n + b
\]

**Смысл z:** «насколько признаки голосуют за класс open».

Учебный мини-пример (вымышленные веса, чтобы посчитать руками):

| признак | значение x | вес w | вклад w*x |
|---------|------------|-------|-----------|
| is_vpn | 1 | 0.4 | 0.4 |
| is_billing | 0 | 0.1 | 0.0 |
| priority | 5 | 0.3 | 1.5 |
| satisfaction | 3 | -0.2 | -0.6 |
| tag_count | 2 | 0.1 | 0.2 |
| bias b | — | — | 0.0 |

\[
z = 0.4 + 0 + 1.5 - 0.6 + 0.2 + 0 = 1.5
\]

- вес priority положительный → высокий priority увеличивает z (чаще open);  
- вес satisfaction отрицательный → высокая оценка чуть тянет к resolved.

Пока z — не вероятность, а «сырой балл» (похож на logit из фазы C).

### 6.4. Шаг 2 — из z в вероятность (сигмоида)

Нужно число от 0 до 1. Используют функцию:

\[
p = \frac{1}{1 + e^{-z}}
\]

Это **вероятность класса 1** (у нас P(open)).

Поведение:


| z | e^(-z) примерно | p = P(open) |
|---|-----------------|-------------|
| 0 | 1 | 0.50 |
| 1.5 | ~0.22 | ~0.82 |
| 3 | ~0.05 | ~0.95 |
| -1.5 | ~4.5 | ~0.18 |

В примере z = 1.5 → P(open) ≈ **0.82**.

Свойства, которые важно запомнить:

1. p всегда между 0 и 1;  
2. чем больше z, тем ближе p к 1;  
3. при z = 0 ровно 0.5;  
4. P(resolved) = 1 − P(open).

Именно это возвращает `predict_proba`: например `[0.18, 0.82]`.

### 6.5. Шаг 3 — из вероятности в метку 0/1

По умолчанию в sklearn:

```text
если p >= 0.5 → predict = 1
иначе         → predict = 0
```

В примере 0.82 ≥ 0.5 → **open**.

Порог 0.5 можно менять в своём коде (например 0.7, если дорого ошибочно считать тикет open) — но `predict()` сам использует 0.5.

### 6.6. Как модель «учится» (fit) — без страха формул

На старте веса случайные/нулевые → предсказания плохие.

Для каждого тикета из train:

1. считают p = P(open);  
2. смотрят правильный y (0 или 1);  
3. если y=1, а p маленькая → ошибка большая (штраф / loss);  
4. если y=0, а p большая → тоже штраф.

**Цель fit:** подобрать веса w и b так, чтобы суммарный штраф на train стал меньше.

Как двигают веса (идея фазы F):

- смотрят, в какую сторону изменить w, чтобы loss упал;  
- делают маленький шаг (оптимизация «под капотом»; `max_iter` — сколько таких попыток максимум).

Это не заучивание строк CSV, а поиск весов.  
Но если модель слишком гибкая и данных мало — можно переобучиться (фаза E): на train отлично, на val плохо. Logistic обычно относительно «простая», поэтому хороший первый выбор.

### 6.7. Что делают аргументы в нашем коде

```python
LogisticRegression(
    max_iter=1000,
    class_weight="balanced",
    random_state=42,
)
```


| Аргумент | Простыми словами |
| -------- | ---------------- |
| `max_iter=1000` | Дай оптимизатору до 1000 шагов, чтобы успел найти хорошие веса |
| `class_weight="balanced"` | Open реже resolved. Без этого модель ленится всегда говорить 0 (как baseline). Balanced сильнее штрафует ошибки на редком классе |
| `random_state=42` | Чтобы при повторном запуске (где есть случайность) результат был стабильнее |
| `C` (по умолчанию 1) | Регуляризация: маленький C → веса не раздуваются → меньше overfitting, но может недообучиться |


### 6.8. Методы API — что вызывать


| Метод | Вход | Выход | Когда |
| ----- | ---- | ----- | ----- |
| `fit(X, y)` | признаки train + метки | обученные веса внутри объекта | только при train |
| `predict(X)` | признаки | массив 0/1 | нужен класс |
| `predict_proba(X)` | признаки | вероятности по классам | нужна уверенность |


В проекте вызываются через Pipeline: `pipe.fit` / `pipe.predict` — снаружи не видно OneHot, но внутри перед logistic он уже отработал.

### 6.9. Связь с majority baseline

Baseline: всегда 0, P по сути «игнорируем признаки».  
Logistic: смотрит признаки и может сказать 1 для «подозрительных» тикетов.

Поэтому accuracy может быть похожа на baseline (много resolved), а **recall/F1 по open** — выше. Это как раз ваш `metrics.json`.

### 6.10. Чего logistic не умеет хорошо

Граница решения по сути **линейная** в пространстве признаков: вклад признаков в z складывается.

Сложные правила вида «open только если vpn И priority≥4 И tag_count=0» она приближает грубо.  
Деревья/бустинг часто лучше на таблицах — следующий шаг после logistic.

### 6.11. Чеклист «я понял logistic»


1. Сначала считается z = сумма (вес × признак) + bias.  
2. Потом p = сигмоида(z) = P(класс 1).  
3. Потом метка по порогу 0.5.  
4. fit подбирает веса, уменьшая ошибку на train.  
5. `class_weight="balanced"` помогает не игнорировать редкий класс.

## 11. `predict` и `predict_proba` (на Pipeline)

После `joblib.load`:

```python
bundle = joblib.load("artifacts/model.joblib")
pipe = bundle["pipeline"]

y_hat = pipe.predict(x_df)           # [0] или [1]
```

## 12. `StandardScaler`

**Модуль:** `sklearn.preprocessing`

```python
StandardScaler()  # (x - mean) / std
```

Иногда ставят перед линейными моделями, если признаки очень разных масштабов.  
Для дерева/бустинга часто не обязателен.  
У logistic с one-hot + пара чисел можно жить без него; добавите, если эксперимент улучшит val.

## 13. `HistGradientBoostingClassifier` (или аналог)

**Модуль:** `sklearn.ensemble`

**Зачем:** сильнее ловит нелинейности («почему бустинг бьёт линейную» на собесе).

Типичные аргументы:


| Аргумент | Влияние |
| -------- | ------- |
| `max_depth` | глубина деревьев; слишком большая → overfitting |
| `learning_rate` | размер шага (идея фазы F) |
| `max_iter` | число деревьев |


Сравнивают с logistic по тому же val и тому же `metrics.json`-стилю.
