# Лекция: Числа для продакшена — p95, cost, токены (Фаза D)

**Для кого:** после фазы C; обязательно до cost/latency в пилоте.  
**Цель:** в design note сами считать $/запрос и говорить про p95, а не только «среднее».  
**Глубина:** арифметика и интуиция, не финмоделирование.

## 0. Зачем эта лекция

Менеджер спросит:

- Сколько будет стоить 1000 запросов/день?
- Уложимся ли в SLA 5 секунд?
- Что даст cache на 40%?

Ответы — из простых расчётов ниже. Без них пилот = «надеемся».

## 1. Проценты, доли, basis points — подробно

Это три способа записать **одну и ту же идею**: «какая часть от целого».

### 1.1. Доля (доля единицы)

Число от **0 до 1**.

| Доля | Смысл |
|------|--------|
| 0 | ничего |
| 0.5 | половина |
| 0.73 | 73 сотых |
| 1 | всё |

Примеры из вашего плана:

- majority baseline **0.73** → 73% тикетов `resolved`;
- Hit-rate@5 = **0.7** → в 7 из 10 вопросов эталон в top-5;
- cache hit **0.4** → 4 из 10 запросов из кеша.

В коде и метриках почти всегда удобнее доля (`0.73`), а человеку говорят «73%».

### 1.2. Процент (%)

\[
\text{процент} = \text{доля} \times 100
\]

| Доля | Процент |
|------|---------|
| 0.73 | 73% |
| 0.015 | 1.5% |
| 0.004 | 0.4% |

«40% cache hit» = доля 0.4 = 40 из 100 запросов.

Аналогия Laravel: `$hits / $total` → доля; `* 100` → процент для UI.

### 1.3. Процентный пункт (п.п.) — не путать с «процентами роста»

**Процентный пункт** — единица шкалы процентов: сдвиг по самой шкале.

- Было **70%**, стало **72%** → выросло на **2 процентных пункта** (+2 п.п.).
- Относительный рост: \(2 / 70 \approx 2.9\%\) — это уже «на сколько процентов от старого значения».

| Было | Стало | п.п. | «На сколько %» относительно |
|------|-------|------|------------------------------|
| 50% | 60% | +10 п.п. | +20% (потому что 10/50) |
| 70% | 77% | +7 п.п. | +10% (7/70) |
| 10% | 12% | +2 п.п. | +20% |

Почему важно: фраза «accuracy выросла на 10%» двусмысленна.

- Имеют в виду +10 п.п. (50% → 60%)?
- Или ×1.10 (50% → 55%)?

В пилоте безопаснее: «было 0.70, стало 0.80» или «+10 п.п.».

### 1.4. Basis points (bps) — «сотые доли процента»

**1 basis point = 0.01 процента = 0.0001 в долях.**

| bps | В процентах | В долях |
|-----|-------------|---------|
| 1 bps | 0.01% | 0.0001 |
| 10 bps | 0.10% | 0.001 |
| 50 bps | 0.50% | 0.005 |
| **100 bps** | **1%** | **0.01** |
| 150 bps | 1.5% | 0.015 |

Откуда слово: в финансах говорят «ставки выросли на 25 bps», чтобы не путать с «на 25%».  
25 bps = +0.25 процентных пункта (например ставка 5.00% → 5.25%), а не «ставка × 1.25».

Связь с п.п.:

- **100 bps = 1 п.п. = 1%** на шкале процентов;
- **1 п.п. = 100 bps**.

Примеры «по-вашему»:

- Hit-rate 70% → 72% = **+2 п.п. = +200 bps**;
- цена API выросла на **50 bps** = +0.5% к цене (не в 1.5 раза!);
- conversion 3.20% → 3.45% = +0.25 п.п. = **+25 bps**.

Для GenAI-пилота bps нужны редко; чаще хватает долей и п.п.  
Но на собесе/в статьях «+50 bps» встречается — теперь читается.

### 1.5. Шпаргалка перевода

```
доля        × 100     → процент
процент     ÷ 100     → доля
1 п.п.                → 1% на шкале = 100 bps
1 bps                 → 0.01% = 0.0001 доля
```

### 1.6. Что использовать в пилоте

| Ситуация | Как писать |
|----------|------------|
| Метрики в коде / JSON | доля: `0.73` |
| Отчёт менеджеру | «73%» или «0.73» |
| Изменение метрики | «+5 п.п.» или «было 0.70 → 0.75» |
| Мелкое изменение ставки/цены | bps (если так принято в компании) |

## 2. Среднее vs медиана vs p95

Одни и те же 9 замеров latency (секунды):

```
1, 1, 1, 2, 2, 2, 3, 3, 30
```

| Метрика | Значение (примерно) | Смысл |
|---------|---------------------|--------|
| **Mean (среднее)** | (1+1+1+2+2+2+3+3+30)/9 ≈ **5 с** | «в среднем» — один выброс 30с сильно тянет вверх |
| **Median (медиана)** | средний по порядку = **2 с** | типичный пользователь; выброс почти не влияет |
| **p95** | 95-й процентиль | «у 95% запросов latency ≤ этого числа» |

### Что такое p95 на пальцах

Отсортировали 100 замеров от быстрых к медленным.  
**p95** ≈ значение на 95-й позиции: 95 запросов быстрее или равны, 5 — медленнее.

В примере из задач фазы D:

- 95 из 100 ≤ 4 с → **p95 ≈ 4 с**
- 5 хвостов до 20 с
- mean будет **выше** 4 с (хвосты тянут среднее вверх)

### Что важнее для SLA

SLA обычно: «95% запросов быстрее X секунд» → смотрят **p95**, не mean.

Почему mean опасен:

- один медленный запрос портит среднее;
- «среднее 3 с» при p95 = 12 с → пользователи часто ждут долго.

Аналогия Laravel: среднее время HTTP-ответа в Telescope vs «95% уложились в 200ms» в APM — второе ближе к обещанию клиенту.

| Вопрос | Смотреть |
|--------|----------|
| Типичный опыт | медиана |
| Обещание SLA / хвосты | **p95** (иногда p99) |
| Грубая ёмкость / cost | mean часто ок |

## 3. Логарифмы как «порядки» (опционально)

Не считать ln руками. Идея: **порядок величины**.

| Было | Стало | Порядок |
|------|-------|---------|
| 100 запросов/день | 1000 | ×10 (один порядок) |
| $0.001 / запрос | $0.01 | ×10 |
| 1K токенов | 1M токенов | ×1000 |

`log10`: сколько раз умножили на 10.  
Для пилота достаточно говорить: «стоимость выросла на порядок» = примерно ×10.

## 4. Стоимость запроса: токены × цена

LLM почти всегда биллит так:

```
стоимость запроса =
    (число input-токенов  × цена за 1 input-токен)
  + (число output-токенов × цена за 1 output-токен)
```

Цены в прайсах обычно пишут **за 1 миллион токенов** (1M), не за один токен.

Поэтому удобный рабочий приём:

```
цена за 1 токен = цена за 1M / 1_000_000

стоимость input  = input_tokens  / 1_000_000 × цена_за_1M_input
стоимость output = output_tokens / 1_000_000 × цена_за_1M_output
стоимость всего  = стоимость input + стоимость output
```

### Пример (задача D2)

Дано:

- input = 1500 токенов  
- output = 400 токенов  
- цена input = **$0.50 за 1M**  
- цена output = **$1.50 за 1M**

Считаем по шагам:

```
input:  1500 / 1_000_000 × 0.50 = 0.00075 $
output:  400 / 1_000_000 × 1.50 = 0.00060 $
итого:  0.00075 + 0.00060 = 0.00135 $ за запрос
```

Итого **$0.00135** за один запрос (примерно 0.135 цента).

Тот же расчёт «в уме»:

1. 1500 токенов — это 1500/1_000_000 = 0.0015 миллиона → × $0.50 = $0.00075  
2. 400 токенов — это 0.0004 миллиона → × $1.50 = $0.00060  
3. Складываем.

### Бюджет на месяц (задача D3)

```
1000 запросов/день × 30 дней × $0.00135 ≈ $40.5 в месяц
```

Грубо, без пиков, ретраев и внезапно длинных ответов.

### Практические множители

- ретраи могут умножить cost на 1.2–2;
- длинный контекст RAG (много чанков) раздувает **input**;
- «напиши подробнее» раздувает **output** (output часто дороже за токен).

## 5. Cache и средний $/запрос

Если cache hit 40% **полностью** экономит вызов LLM:

- 40% запросов → $0  
- 60% запросов → полная цена (например $0.00135)

```
средний $/запрос ≈ 0.60 × 0.00135 = 0.00081 $
```

Было $0.00135 → стало $0.00081: осталось **60%** цены, экономия **40%** среднего чека (в этой простой модели).

Нюанс: у cache тоже может быть своя цена (Redis), но для грубой оценки пилота формулы выше достаточно.

## 6. Throughput и p95 (идея)

**Throughput** — сколько запросов в единицу времени тянет система.

Грубая оценка «в один поток»:

- если один запрос занимает p95 = 4 с, то один воркер ≈ 1/4 = **0.25 req/s**  
- 10 параллельных воркеров ≈ 2.5 req/s (очень грубо, без очередей)

Для пилота важно:

1. измерить p95 latency end-to-end (retrieve + LLM);
2. прикинуть пиковый RPS;
3. понять, хватит ли concurrency / нужен ли queue.

Точная формула зависит от архитектуры; на старте достаточно связать: **медленный p95 → меньше пропускная способность**.
