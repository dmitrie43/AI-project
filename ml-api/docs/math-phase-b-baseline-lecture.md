# Лекция: Baseline (Фаза B)

**Для кого:** GenAI Engineer plan, после Precision / Recall / F1.  
**Цель:** уметь за 2 минуты объяснить, что такое baseline, зачем он, как считать majority baseline и с чем сравнивать RAG.

**Связь с кодом:** `data-pipeline` → `report.py` → блок *Baseline without ML* в `report.md`.

---

## 0. Зачем эта лекция

Вы уже умеете считать accuracy, precision, recall, F1.  
Остаётся вопрос: **цифра сама по себе ничего не значит**.

«Модель угадывает статус в 78% случаев» — хорошо это или плохо?  
Без точки сравнения — неизвестно.

Эта точка и называется **baseline**.

---

## 1. Определение

**Baseline** — самое простое правило (или текущая система), с которым вы сравниваете свою модель.

Это не цель и не «идеальная модель». Это **пол**:

> Если умная модель не лучше тупого правила — внедрять нечего.

### Аналогия из Laravel

Прежде чем писать сложный `TicketPriorityService` с ML, вы проверяете:

> «А если всегда ставить priority = самый частый?»

Если сервис почти не лучше этого правила — сложность не окупается.

---

## 2. Главный пример: majority baseline

### Правило

1. Смотрим датасет: какой класс встречается чаще всего (**majority class**).
2. На любом новом примере **всегда** предсказываем этот класс.
3. Считаем метрику (обычно accuracy).

Никакого текста тикета, никаких эмбеддингов — только «что чаще бывает».

### Пример А (как задача B1)

| Статус | Количество |
|--------|------------|
| `resolved` | 90 |
| `open` | 10 |
| **Всего** | 100 |

Majority class = `resolved`.  
Baseline: всегда говорить `resolved`.

Результат:

- 90 раз угадали верно;
- 10 раз ошиблись (`open` назвали `resolved`);
- **Accuracy = 90/100 = 0.90 (90%)**.

### Почему 90% — не успех

1. Модель **не смотрит** на содержимое тикета.
2. Класс `open` она **никогда** не предсказывает → recall по `open` = 0.
3. Для поддержки часто важны как раз редкие `open` / `urgent`.
4. Любая «настоящая» модель должна **бить** эти 90%, иначе она хуже тупого правила.

### Тот же пример через confusion matrix

Пусть ДА = `resolved`. Baseline всегда говорит ДА:

|  | Факт: resolved | Факт: open |
|--|----------------|------------|
| Предсказали resolved | TP = 90 | FP = 10 |
| Предсказали open | FN = 0 | TN = 0 |

- Precision(`resolved`) = 90/100 = 0.90  
- Recall(`resolved`) = 90/90 = 1.00  
- Recall(`open`) = 0  

Вывод: baseline отлично выглядит на частом классе и полностью игнорирует редкий.

## 3. Откуда в data-pipeline берётся «~73%»

В отчёте пайплайна есть блок вроде:

> Самый частый status = `resolved` (73% строк).  
> Любая модель должна бить этот baseline.

**73% — это не качество нейросети.**  
Это просто доля самого частого статуса в clean-данных.

Как считается в коде (`report.py`):

1. `status.mode()` → самый частый статус;
2. `baseline_majority_share` → доля строк с этим статусом;
3. эта доля = accuracy majority baseline (если всегда предсказывать mode).

Пересобрали датасет — процент изменится. Смысл тот же: **пол для будущей модели**.

---

## 4. Живой мини-кейс «модель vs baseline»

Представьте val-набор: 100 тикетов, majority = `resolved` (80%).

| Система | Accuracy | Recall по `open` |
|---------|----------|------------------|
| Majority baseline | 0.80 | 0.00 |
| Модель A | 0.78 | 0.10 |
| Модель B | 0.85 | 0.40 |
| Модель C | 0.76 | 0.70 |

Как читать:

- **A (78%)** — хуже пола по accuracy, почти не ловит `open` → в прод не берём.
- **B (85%)** — бьёт baseline и лучше ловит `open` → хороший кандидат.
- **C (76%)** — accuracy ниже baseline, но recall по `open` сильно вырос.  
  Имеет смысл, **если** бизнесу критично не пропускать `open`, и вы готовы терпеть больше ошибок на `resolved`. Тогда сравнивайте не только accuracy, а ещё F1/`open`-recall.

Правило лекции:

> Сначала сравнили с baseline. Потом спорим, какая метрика важнее бизнесу.

## 5. Другие виды baseline (чтобы не думать, что majority — единственный)

| Тип | Что делает | Когда полезен |
|-----|------------|---------------|
| **Majority** | всегда самый частый класс | старт для классификации |
| **Случайный** | угадывает случайно | нижняя планка «хуже random — баг» |
| **Простое правило** | например `priority >= 4 → urgent` | часто сильнее majority; честный бизнес-пол |
| **Старая система** | текущий бот / keyword-поиск | пилот: «новый подход лучше старого?» |
| **Человек** | разметка оператора | потолок качества, не пол |

На практике для табличных тикетов хватает:

1. majority;
2. одно простое if-правило.

## 6. Baseline для RAG (поиск документов)

В RAG мы не предсказываем `resolved`/`open`.  
Мы возвращаем top-k чанков. Majority-класс тут не подходит.

### Что тогда считать полом?

| Baseline | Идея |
|----------|------|
| Random@k | k случайных документов |
| Popular@k | всегда одни и те же «популярные» статьи |
| Keyword / LIKE | поиск по словам без эмбеддингов |

### Пример с Hit-rate@5

Напоминание: **@5** = смотрим первые 5 документов на вопрос.  
**7/10** = у 7 вопросов из 10 нужный doc попал в эту пятёрку.  
Это не «top-7».

| Метод | Hit-rate@5 |
|-------|------------|
| Keyword baseline | 0.45 |
| Embeddings | 0.70 |

Смысл: векторы реально улучшили поиск (+0.25), а не просто «звучат современно».

Если embeddings дают 0.47 при keyword 0.45 — пользы почти нет, пилот под вопросом.

---

## 7. Как честно сравнивать с baseline

1. **Та же метрика** — accuracy с accuracy, Hit-rate@5 с Hit-rate@5.
2. **Тот же набор** — val/test, не «baseline на всём, модель на лёгком куске».
3. **Тот же k** в RAG.
4. **Не только accuracy** при дисбалансе — смотрите precision/recall/F1 по важному классу.
5. **Сначала baseline, потом ML** — иначе оптимизируете в вакууме.

---

## 8. Частые ошибки

| Ошибка | Почему ломает выводы |
|--------|----------------------|
| «У нас 85% — значит хорошо» без baseline | Нет масштаба |
| Путать baseline с целью | Baseline = пол; цель может быть «hit-rate@5 ≥ 0.8» |
| Хвалить RAG без keyword-пола | Могли остаться на обычном поиске |
| Считать majority успехом | Это статистика датасета, не интеллект |
| Игнорировать редкий класс | Бизнес-риск (пропущенный `open`/`urgent`) |

## 9. Шпаргалка для собеса (30–40 секунд)

**Классификация тикетов**

> Сначала считаю majority baseline: доля самого частого `status`.  
> Модель должна бить этот пол на validation.  
> Одной accuracy мало — смотрю precision/recall по редким классам, потому что majority легко набирает высокую accuracy и при этом recall по `open` = 0.

**RAG**

> Baseline — keyword-поиск или popular docs.  
> Метрика — Hit-rate@k на golden-вопросах при фиксированном k.  
> Эмбеддинги внедряю, только если hit-rate заметно растёт.

---

## 10. Связь с соседними темами фазы B

```
Confusion / P / R / F1  →  как мерить ошибки
Hit-rate@k              →  как мерить поиск (RAG)
Baseline                →  с чем сравнивать любую цифру   ← эта лекция
Train/val + leakage     →  чтобы сравнение было честным
```

Baseline на «грязном» val с leakage тоже врёт: цифры красивые, в проде — нет.  
Поэтому пол считают на том же честном split, что и модель.
