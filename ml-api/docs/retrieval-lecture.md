## 0. Зачем это в продукте

Internal Assistant отвечает по внутренним докам. LLM **не знает** вашу wiki сама по себе.

Нужен шаг **retrieve** (найти куски текста):

```
вопрос → найти top-k релевантных документов → (позже) отдать их в LLM → ответ
```

Неделя 5 учит первую половину: **как искать**. Генерацию ответа (LLM) — позже.

---

## 1. Корпус (corpus)

**Корпус** — набор документов, по которым ищем.

У вас: `data/corpus/*.md` (runbook’и: VPN, SSO, onboarding…).

Каждый файл сейчас = **один чанк** (кусок текста для индекса).  
В проде длинный PDF режут на много чанков — идея та же, только больше кусков.

Аналогия Laravel: «каталог статей» в таблице `articles`, по которому идёт поиск.

---

## 2. Эмбеддинг (embedding)

**Эмбеддинг** — вектор чисел, который модель строит из текста так, чтобы **похожий смысл → похожие векторы**.

Пример:

- текст: `"cannot connect vpn"`
- модель: `all-MiniLM-L6-v2`
- выход: массив из **384** чисел

Это не «перевод на другой язык», а **координаты смысла** в многомерном пространстве.

### Чем отличается от игрушечного cosine-demo

| | Toy demo | Сейчас |
|--|----------|--------|
| Вектор | вручную `[0.9, 0.1, 0]` | модель `encode(text)` |
| Размер | 3 | 384 |
| Смысл | вы придумали оси | модель выучила на огромном тексте |

**Математика сравнения та же** — cosine / top-k.

### Что модель *не* делает

- не отвечает на вопрос;
- не «понимает» как человек;
- только кодирует текст в вектор для сравнения.

---

## 3. Encoder / SentenceTransformer

**Encoder** (у нас `SentenceTransformer`) — программа, которая вызывает embedding-модель:

```text
текст → encode → numpy-вектор
```

Параметр `normalize_embeddings=True` сразу делает длину вектора ≈ 1.  
Тогда cosine упрощается до **скалярного произведения** (dot).

Модель скачивается с Hugging Face при первом запуске и кэшируется локально.

---

## 4. Индекс (index)

**Индекс** — заранее посчитанные эмбеддинги корпуса + метаданные документов.

У вас артефакты:

| Файл | Содержимое |
|------|------------|
| `embeddings.npy` | матрица `[число_доков × 384]` |
| `meta.json` | id, путь, полный текст, имя модели |

### Зачем заранее

Считать эмбеддинги всех доков на **каждый** вопрос дорого.  
Один раз `build` → много раз быстрый `search` (кодируется только вопрос).

Аналогия: как поисковый индекс Elasticsearch, только вместо BM25 — векторы.

### Когда пересобирать

Изменили/добавили `.md` в корпусе → снова:

```powershell
uv run python -m app.retrieval.build
```

---

## 5. Query embedding

**Query** — вопрос пользователя.

На поиске:

1. `encode(query)` → вектор вопроса;
2. сравнить с **каждой** строкой матрицы документов;
3. взять лучших.

Важно: вопрос и документы кодирует **одна и та же** модель (`model_name` в meta). Иначе пространство смыслов разъедется.

---

## 6. Cosine similarity (напоминание)

\[
\cos(a,b) = \frac{a·b}{|a|·|b|}
\]

| Значение | Смысл |
|----------|--------|
| близко к 1 | направления похожи → тексты семантически близки |
| около 0 | мало общего |
| низкое / отрицательное | нерелевантно |

После нормализации: `score = doc_matrix @ query_vector`.

Это **не** вероятность класса из logistic.  
Это **похожесть** двух векторов (другая задача).

---

## 7. Top-k

**Top-k** — взять k документов с наибольшим score.

Пример: k=3 → три лучших чанка для будущего RAG.

Больше k → выше шанс попасть в нужный док (hit-rate↑), но больше мусора в контексте LLM.

Связь с math B: Hit-rate@k = доля вопросов, где эталон попал в top-k.

## 8. Retrieval vs `/predict` (не путать)


| | `/predict` (неделя 4) | Retrieval (неделя 5) |
|--|----------------------|----------------------|
| Вход | табличные признаки тикета | текст вопроса |
| Модель | LogisticRegression | Embedding encoder |
| Выход | класс `is_open` + proba | список документов + cosine |
| Смысл | классификация | поиск похожего текста |


Оба живут в ml-api, но решают **разные** задачи.

## 9. Semantic search vs keyword (задел под BM25)

**Semantic (vector):** ищет по смыслу.  
«не коннектится удалёнка» может найти `vpn-reset.md`, даже без слова VPN в запросе (если модель хорошо обобщает).

**Keyword (BM25 и т.п.):** ищет по совпадению слов/терминов.  
Силён на точных кодах ошибок, id, редких названиях.

**Hybrid:** часто комбинируют оба (потом + rerank).

BM25 подробнее — на шаге 2 недели 5.

## 10. RAG (куда это ведёт)

**RAG = Retrieval-Augmented Generation**

1. Retrieve — наш mini-retriever  
2. Augment — вставить найденные чанки в промпт  
3. Generate — LLM пишет ответ с опорой на чанки  

Пока сделан только пункт 1.

## 11. Поток в вашем коде


| Шаг | Команда / модуль | Что происходит |
|-----|------------------|----------------|
| Корпус | `data/corpus/*.md` | сырые тексты |
| Build | `python -m app.retrieval.build` | encode всех доков → `.npy` + `meta.json` |
| Search | `python -m app.retrieval.cli_search "..."` | encode вопроса → cosine → top-k |


В `search.py`:

1. `load_index()` — матрица + meta  
2. `model.encode(query)` — вектор вопроса  
3. scores = cosine ко всем докам  
4. `argsort` → top-k  
5. вернуть id, score, snippet

## 12. Важные ограничения (прод)

1. **Качество корпуса** важнее тонкой настройки модели.  
2. Плохой chunking (слишком длинный/короткий кусок) ломает поиск.  
3. Полный перебор всех векторов ок для десятков/тысяч чанков; для миллионов нужен ANN-индекс (pgvector HNSW и т.д.).  
4. Высокий cosine ≠ «факт верный» — только «похоже по смыслу».  
5. Один и тот же `model_name` на build и search.

## 13. Шпаргалка терминов


| Термин | Одной фразой |
|--------|----------------|
| Corpus | набор документов для поиска |
| Embedding | текст → вектор смысла |
| Encoder | модель/библиотека, которая считает embedding |
| Index | сохранённые векторы корпуса + meta |
| Query | вопрос пользователя |
| Cosine | мера похожести двух векторов |
| Top-k | k лучших по score |
| Retrieval | этап «найти чанки» |
| RAG | retrieve + LLM generate |
| BM25 | keyword-ранжирование (не vector) |
| Chunk | кусок документа в индексе |
